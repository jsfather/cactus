# Panel history, site settings and support

## Implemented

- Student names in the administrator's list open a dedicated student record.
- The record displays all existing enrollments, total paid and pending order amounts, paid order-line amounts per term, attendance/grades, and successful sign-ins. Orders, attendance and sign-ins are paginated in batches of 50 using the history page number. Order creation dates are not represented as payment settlement dates.
- Successful OTP/password sign-ins and initial registration append a minimal login audit record in the same database transaction as the session. No password, session token, IP address or user agent is copied into this history. Signing out only removes the active session. Historical sign-ins before activation cannot be recovered.
- Login audit records are system-generated and intentionally have no manual create/edit/delete UI or fabricated starter entry. Account deletion removes its audit records through the foreign key.
- Site settings include bilingual default SEO titles/descriptions, a Google Search Console verification token, and up to 12 secure external social links. Existing saved settings receive defaults for new fields. Social links render in the public footer; verification renders through Next's metadata API on both public roots.
- Shared panel date pickers and date rendering use the Persian calendar in both locales. Canonical persisted date values remain Gregorian ISO values.
- Shared form sidebar fields no longer inherit a two-column span inside a one-column sidebar. Forms without a sidebar no longer reserve an empty column.
- Ticket messages use a compact conversation layout showing the latest 200 messages. Administrator views include requester identity and recent terms with a link to a student's full record.
- Ticket summaries distinguish new, waiting, answered and closed conversations without changing existing persisted status values: `open` means waiting for support; `pending` means a support reply has been sent. New tickets are open tickets containing at most the initial message.

## Subsequent implementation

1. Live chat: `/panel/admin/live-chat`, `/panel/admin/live-chat/settings` and `/panel/teacher/live-chat`. The bilingual public widget appears after ten seconds and collects a name and Iranian mobile number. Private HTTP-only visitor cookies authorize that visitor's history. Messages and conversation history have paginated reads. Operators are configured from active administrators/teachers; inbox heartbeats expire after 90 seconds. In-office new conversations are assigned to the least-loaded online configured operator; unassigned conversations can be claimed. Administrators can supervise, claim/reassign to themselves, and delete closed conversations with confirmation. Only the assigned operator can send staff messages/images. Visitors and operators can close conversations.
2. Inactivity closure is evaluated on API reads/writes; an open widget polls every five seconds. There is no background scheduler when no clients are connected, so the persisted status is materialized on the next interaction. Eligibility to send is checked against expiry before every send. Default inactivity is ten minutes, configurable alongside Tehran office hours/days, bilingual greeting/away text, logo and color.
3. Chat images are JPEG/PNG/WebP up to 5 MB, checked against binary signature and declared MIME type. They are stored under the existing persistent private upload root and served with authorization, no-store and nosniff headers. Each conversation is capped at 20 images; aggregate anonymous image uploads are capped at 250 MB per rolling day. New conversations have a global cap of 500 per rolling day. These database-backed global caps limit abuse across processes; they are not a substitute for deployment-level rate limiting. Never publicly expose the private upload folder.
4. Tickets support two-minute WebM/Opus voice recordings through the authenticated attachment pipeline. The browser must support MediaRecorder WebM/Opus and grant microphone access (HTTPS is required outside localhost). Binary container markers are checked; this is not media transcoding or malware scanning. Ticket create/reply actions now accept only uploaded private attachment URLs; existing historic external links remain readable. File-only/voice-only messages are accepted. A closed ticket owner can set/change/remove a 1–5-star rating, tied server-side to the latest actual staff responder. A later staff reply clears the prior rating.
5. Academic model: `course_templates` -> `academic_years` / `academic_semesters` -> existing `terms` as individual course offerings -> existing enrollments and results. Add/edit/delete catalog items from `/panel/admin/academic/semesters`. Referenced catalog items cannot be deleted. New offerings require a semester and course template; legacy offerings retain nullable links until deliberately assigned. Selecting a template pre-fills a new offering without sharing its enrollment container.
6. Semester archive uses a confirmation dialog, completes active enrollments, marks its offerings completed/archived and retains their schedules, attendance and grades. Archived offerings cannot be edited/deleted/enrolled into, and attendance writes recheck archive status inside their transaction. The existing participant term/history pages keep these records visible. This locks enrollment/attendance history, not a separately materialized snapshot of all exam/homework entities. Template edits retain old offering text; the level of an already-used template cannot be changed.
7. Startup installs one initial academic year/semester/template and live-chat settings once, through unique seed markers. It does not move legacy offerings or invent historical chat/voice/rating events.
